Chain Checker

A test bench for LLM chains: score a chain against a labelled corpus, then let a second LLM rewrite its system prompt, epoch by epoch, until it scores higher.
This document describes how the checker and the training loop work.

LLM in the loop labelled YAML corpora accuracy first, tokens second resumable runs

What is Chain Checker?

An LLM chain is a prompt, a model and a parser wired together. Whether it works is usually judged by reading a handful of outputs, and whether a prompt change helped is judged the same way. Chain Checker replaces that with a measurement. A chain runs against a fixed corpus of cases, each with an expected output, and every key of the real output is compared with the label. The result is an accuracy, a token count and a list of every case the chain got wrong.

On top of that measurement sits a training loop. Each epoch it scores the chain, hands the prompt and the report to a separate modifier LLM, and asks it for a better prompt. The next epoch scores the new prompt and the loop repeats. The goal is a prompt that scores higher without costing more tokens, found by the loop rather than by hand.

It is written in Python on LangChain and Pydantic. The modifier runs either through a LiteLLM proxy or on a local Ollama server, so a small local model can tune the prompt of a larger hosted one.

The corpus

A corpus is a YAML file of cases. Each case has an id, the input the chain receives and the output keys it is graded on. An optional info block is carried along for a human reader and never compared.

cases:
  - id: 2
    input:
      text: "With ACME, your home just works."
      threshold: 0.8
    output:
      verdicts:
        brand-uppercase: true
        no-exclamation-spam: true
      passed: true

Everything is checked before the first model call. That covers ids that are unique and safe as file names, inputs that match InputSchema exactly, and output keys that the chain's OutputSchema actually declares. The label may check just a subset of the output. A broken corpus fails in a second, not after the fortieth paid call.

Held-out cases. A second corpus passed as --val-file is scored every epoch for the report only. The modifier never sees it, so it shows whether a gain carries over to cases the rewrite had no access to.

What a chain must expose

The checker finds a chain by name in the host project's registry and reads a few class attributes from it:

NameRole
namethe chain type that --chain-type selects
InputSchemavalidates each case's input before the chain runs
OutputSchemadeclares every key a label may check
tierthe LLM tier build() is called with; --chain-tier overrides it
build()returns the LangChain Runnable that answers a call

To be trainable, a chain also keeps its prompt in a module-level SYSTEM_PROMPT string, which the loop replaces directly. If the prompt has placeholders filled with live data, the prompt is split into three pieces:

  1. SYSTEM_PROMPT: the rewritable template, the only piece the modifier edits.
  2. generateSystemPrompt(payload): resolves the template on every call, so a placeholder always renders current data. Its return value is exactly what the modifier reads.
  3. insertInput(prompt, payload): appends the case's own data. The modifier never sees it, so a rewrite cannot overfit to a single input.

Metrics

Each output key is graded by a metric that matches its type. Booleans, floats, keywords, lists, pairs and single values each have their own comparison.

MetricMeasures
Accuracyshare of cases where every checked value matches the label, overall and per rule
Parsingreplies that produced a scoreable answer vs. replies that did not
Tokensprompt, completion and total tokens of the chain, and separately of the modifier
Mispredictedevery wrong case with its input, expected and actual value, which is what the modifier reads

Replies that are almost JSON, such as an unescaped quote inside a string or reasoning wrapped in <think> tags, are repaired before parsing. A chain is graded on what it answered, not on how the model formatted it.

The training loop

One epoch has four steps:

  1. Record. This epoch's prompt and metrics become a new run record, kept raw and rendered afresh on every build.
  2. Build. Fixed instructions, the run history, a per-rule trend table and the steering notes are put together into one instruction.
  3. Ask. The whole instruction goes to the modifier in a single call, with no chat history and no second turn.
  4. Extract. The new prompt is cut out of the reply and becomes SYSTEM_PROMPT for the next epoch.

The modifier is always a separate model from the chain under test. --modifier-tier and --chain-tier are independent, so a cheap model can rewrite the prompt of an expensive one or the other way round.

What the modifier reads

#BlockIncluded
1System instructions: role, how to read the run history, how to diagnose, how to rewritealways
2METRIC-DEFINITIONSwhen a metric has a description
3Run-0 … Run-N: prompt, accuracy, false examples, parse failuresone per epoch, old runs pruned
4RULE-TREND: per-rule accuracy and error direction across every runmulti-rule chains
5Steering noteswhen their input is known
6One closing notezero false examples, or stagnation
7NEW-LLM-PROMPT marker, where the reply startsalways

The instructions set a priority order. Parse failures come first. Then every false example is read against the wording that governs it, then patterns the prompt never states, and finally cases that fail in every run, which point to a bad label rather than a bad prompt. A rewrite should test one hypothesis, should rest on a pattern shared by several failures rather than a single case, and should not grow the prompt overall. Accuracy always wins. Tokens only matter once no false examples are left.

History pruning. Printing every run in full makes the instruction grow without bound. Only the latest two runs, the best run overall and the best run for each rule are printed in full. Every other run shrinks to a one-line stub with its accuracy. A case's input is printed by the first shown run that gets it wrong, so pruning never loses an input.

Steering: small steps, then a restart

A sampled model scores the same prompt differently from run to run, so a free rewrite each epoch mostly wanders. The notes push the other way: small steps from the best prompt so far.

NoteTells the modifier
MEASUREMENTeach score rests on N cases and one case moves it by 1/N, so a few cases are noise
BASERun-K scored best and the latest run did not beat it, so write Run-K's prompt plus one change
LENGTH BUDGETthe base prompt has N characters; stay within N plus 10%, and add by merging or deleting

When small steps stop paying off, the loop changes mode. If two runs in a row fail to beat the best score by more than 0.02, a stagnation note lifts the "keep what works" rule and asks for a new prompt from scratch. The best prompt stays in the history, so a failed restart costs one run. Once a run has no false examples, a different note allows a free rewrite whose only goal is fewer tokens.

Overall accuracy per runRuns without gainNote
0.60 → 0.65 → 0.70 → 0.750none
0.70 → 0.81 → 0.80 → 0.792stagnation, base = Run-1
0.800 → 0.810 → 0.8152stagnation, every step within noise
0.80 → 0.80 → 0.80 → 0.900none, a real gain resets the count

Caching and resuming

Every prediction is written to <id>.txt as soon as it arrives. --continue resumes the newest run made with the same chain, tier and prompt. Cached cases are recalled and only missing ones are sent to the model. A run made with anything else is never continued, so a resumed score always belongs to one configuration. A resumed training loop replays every past epoch into the modifier's history without calling the LLM, so it sends exactly the history an uninterrupted loop would have sent.

Running it

# one pass over the corpus
python bin/checker.py --type <type> --chain-type template_checklist

# four epochs of prompt rewriting, modifier on a local Ollama model
python bin/trainingLoop.py --type <type> --chain-type template_checklist \
    --epochs 4 --modifier-backend ollama --modifier-model qwen3.5:4b

# same, with a held-out corpus scored every epoch
python bin/trainingLoop.py --config my_run.yaml --val-file val.yaml

Every flag can also come from a .yaml or .json config file, with keys spelled like the flags. An unknown key fails loudly and lists the valid ones.

Not standalone. Chain Checker is a package inside a Django host project. The host supplies the bin/ entry points, the chain registry and the app config that hands out a chat model per tier.
