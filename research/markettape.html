What is Market Tape?

Market Tape is a live event board built the way a control room builds a rundown: a timed list of what is about to happen, a lamp next to whatever is currently on air, a countdown to the next cue, and a stage that opens the feed and fills in the numbers the moment they land. It covers the two event classes that actually move the tape intraday — Federal Reserve appearances (FOMC decisions, the Chair's press conference, congressional testimony, governor speeches) and earnings releases for a user-defined watchlist.

The interesting part is not the interface. It is where the data comes from. There is no calendar API, no earnings-date vendor, no IR-webcast registry and no wire feed behind this page. Every schedule row, every stream URL and every reported figure is produced at runtime by Claude with the web-search tool, under a strict JSON response contract, and then normalized and validated by the client. The application is, in effect, a typed UI layer over a search-grounded model — an experiment in how far the model as the data source can be pushed for a domain that normally requires four separate paid integrations.

The thesis: for low-frequency, publicly-announced, text-shaped data — event calendars, webcast links, headline figures against consensus — a search-grounded model with a hard output schema can replace the vendor integration entirely, provided the client treats every response as untrusted and degrades honestly when it is wrong.

① The shape of the app

The whole thing is one MarketTape() component — roughly 820 lines including its own stylesheet — with two subviews (Readout for the results block) and a handful of pure helpers. There is no router, no state library and no build-time data. Startup is a single call into load(), which fires the Fed query and the earnings query in parallel and merges the two result sets into one time-ordered rundown.

load()
Promise.allSettled( fedPrompt(today), earningsPrompt(today, watchlist) )
↓
askClaude()
POST /v1/messages with web_search_20250305 → text blocks
↓

balanced-brace scan · truncation salvage · JSON.parse
↓
normalize()
drop rows without date/title · coerce kind · filter link URLs · resolve ET → epoch ms
↓

day-grouped rundown · lamp state per row · countdown to the next cue
↓
on selection
streamPrompt (find feed + links) · resultPrompt (pull the numbers, repeat every 90 s while live)

Two things follow from this design. First, the app has no persistent dataset — state is the current rundown plus a per-event result cache keyed by event id, both discarded on reload. Second, correctness is a client-side concern: the model is treated as an unreliable upstream, and every field it returns passes through normalize() before it reaches the DOM.

② Three prompt contracts

All three prompts share the same discipline: state today's date explicitly (the model cannot be trusted to know it), demand only compact JSON with no prose and no markdown fences, cap the item count, fix the exact key set with an inline example, and constrain the enumerations.

ContractWhenReturnsWindow
fedPrompt on load / refresh ≤ 6 Fed events: decisions, pressers, testimony, speeches today → +10 days
earningsPrompt on load / watchlist change ≤ 6 confirmed earnings dates for the watchlist tickers today → +21 days
streamPrompt on demand, per event a primary feed URL plus ≤ 4 labelled links —
resultPrompt on demand, then every 90 s while live headline, ≤ 4 metrics vs. estimate, ≤ 3 bullets, price reaction, as-of stamp —

The anti-hallucination clauses

Three rules do most of the work of keeping the board honest:

// every schedule and stream prompt ends with some form of:
streamUrl must be a real URL you saw in the search results — never invent a URL.
skip any ticker with no scheduled date.
if the date is estimated rather than confirmed, start the note with "Est:".

The omission rule matters more than it looks. Without it, a model asked for "earnings dates for these five tickers" will tend to return five rows, because five were asked for — inventing a plausible date for the one company that has not announced. Explicitly licensing an empty result is what turns the response from a guess back into a report. The "Est:" prefix is the same idea applied to confidence: the note field carries its own uncertainty marker straight into the UI rather than dropping it silently.

The result contract has one further clause — "Write every field in your own words — do not quote source text" — and a dedicated status: "not_yet" value, so that "the numbers are not out" is a first-class answer with an empty metrics array instead of a fabricated table. The readout renders that state as an explicit nothing published yet panel with a re-check button.

Metric verdicts

Each metric returns {label, actual, estimate, verdict} with verdict constrained to beat / miss / inline, which the UI maps directly to colour. The prompt shape differs by event class — four earnings slots (EPS, revenue, a segment or margin, guidance) versus four Fed slots (target range, vote split, dot-plot median, balance sheet) — so a rate decision and a quarterly report render through the same component without a branch in the view layer.

③ Surviving imperfect JSON

A model told to emit only JSON will still occasionally wrap it in a fence, prefix it with a sentence, or — the failure that actually hurts — get cut off by the token limit mid-array. The parser handles all three without a retry:

// find the first [ or {, then walk the string tracking depth,
// string state and escapes — braces inside strings must not count
if (c === '"') { inStr = true; continue; }
if (c === "[" || c === "{") depth++;
else if (c === "]" || c === "}") {
  depth--;
  if (depth === 1 && open === "[") lastItem = i;  // last complete element
  if (depth === 0) { end = i; break; }
}

If the scan closes cleanly, the balanced slice is parsed. If it never closes and the payload is an array, the parser falls back to s.slice(0, lastItem + 1) + "]" — everything up to the last element that did close, re-terminated. A truncated response therefore degrades to a shorter rundown instead of an error banner. Fences are stripped first; leading prose is skipped by seeking the first bracket; and the string-state tracking is what keeps a ] inside a note field from ending the scan early.

Design note: salvage beats retry here. A retry costs another search round-trip and can come back differently; recovering four of six scheduled events immediately is the better trade for a board whose whole value is being up to date.

④ Exchange time without a tz library

Every event in this domain is announced in New York wall-clock time — "2:00 p.m. ET", "after the close" — but must be rendered as a countdown in the viewer's own local time, and the two differ by an offset that changes twice a year. The app carries no timezone database. Instead it inverts Intl.DateTimeFormat:

// what does this instant look like in New York?
function tzOffsetMin(ts) {
  const p = tzParts(ts);                       // formatToParts in America/New_York
  const asUTC = Date.UTC(+p.year, +p.month-1, +p.day, +p.hour, +p.minute, +p.second);
  return (asUTC - ts) / 60000;
}

// invert it: from a New York wall clock back to a real instant
let ts = naive - tzOffsetMin(naive) * 60000;   // first guess
ts     = naive - tzOffsetMin(ts)    * 60000;   // re-solve at that instant

The forward direction — instant to New York parts — is something every browser already does correctly, DST included. The inverse is a fixed-point solve: guess the offset using the naive timestamp, then recompute it at the resulting instant. The second pass is what gets the hours immediately around a DST transition right, where the first guess lands on the wrong side of the change. Two iterations converge for every case that matters here, and the whole timezone layer costs about fifteen lines with no dependency.

The same primitives drive the rest of the clock furniture: etToday() for the date handed to every prompt, etClock() for the ticking ET readout in the header, dayLabel() for Today / Tomorrow / weekday grouping in the rundown, and countdown() for the T− 00:14:32 cue.

⑤ The on-air state machine

Each row resolves to one of three states, recomputed every second against a 1 Hz clock tick:

StateConditionRendering
livestart ≤ now < start + windowpulsing red lamp, On air tag, auto-refreshing readout
donenow ≥ endhollow lamp, Done tag
scheduledotherwisegrey lamp; amber if it is the next cue

Two details make this behave like a real rundown rather than a calendar. First, earnings have two timestamps — releaseET, when the numbers hit the wire, and timeET, when the call starts — and the live window opens at min(releaseTs, ts), because the market reacts to the press release, not to the webcast half an hour later. The row surfaces both (Numbers 16:30 · call 17:00) and the countdown targets whichever comes first. Second, the window length is per class:

const LIVE_WINDOW_MIN = { fed: 95, earnings: 80 };

A statement plus a Chair press conference runs longer than a typical earnings call, and the window is what decides how long the app keeps polling for results — so it is sized to the event, not to a global default.

The header countdown is fed by a next selector that prefers any live event over the nearest upcoming one, and the hairline progress bar under the header ramps across the final three hours before the cue (span = 3 × 3600000), pinned to 4 % beyond that so it never reads as empty.

⑥ The stage: feeds and readouts

Feeds are classified, not assumed

Every event carries a streamKind of video, audio or page, and the stage says plainly which one it got. Only a recognized YouTube id — matched against watch, live/, embed/ and youtu.be forms — offers in-page playback. Most earnings calls are listen-only IR webcasts that refuse to embed, so the app tells the user exactly that and hands them an Open live stream ↗ button instead of an empty black rectangle. When no usable feed was found, a Find stream & links button runs streamPrompt on demand and merges the result back into that one event.

Anti-pattern avoided: silently rendering an iframe that will be refused by the host. Classifying the feed up front and saying why it opens in a new tab is the difference between an app that looks broken and one that is merely honest about the web.

The readout auto-refreshes only while it matters

useEffect(() => {
  if (!auto || !sel || !selLive) return;
  fetchResult(sel);
  const t = setInterval(() => fetchResult(sel), 90000);
  return () => clearInterval(t);
}, [auto, sel && sel.id, selLive, fetchResult]);

Polling is bounded on three sides: it runs only for the selected event, only while that event is inside its live window, and only while the user leaves the Auto toggle on. Everything else is a manual Get result press. Each poll is a fresh search — which is the point, since a readout taken two minutes after the release and one taken at the end of the call are genuinely different answers — and results are cached per event id so switching rows costs nothing.

Watchlist

The watchlist is capped at twelve tickers, sanitized to [A-Z0-9.-], de-duplicated, persisted through the host storage API and — importantly — reloads the rundown on every change, because the earnings query is parameterized by exactly that list. Four always-on channels (the Fed's own broadcast page, Bloomberg TV, Yahoo Finance, Schwab Network) are hard-coded as a fallback for when nothing scheduled is on air.

⑦ Failure behaviour

The board is built to be partially wrong in public rather than blank. Four layers:

  • Independent queries. Promise.allSettled means a failed Fed lookup does not take the earnings rows down with it; the banner names what is missing ("Couldn't load Fed events. The rest of the rundown is current.") and the rest renders.
  • Row-level validation. normalize() drops anything without a date and title, coerces the event class, discards links that are not http(s) URLs, and filters out rows whose timestamp fails to resolve — a malformed date removes one row, not the page.
  • Seed fallback. If the live lookup returns nothing usable at all, a small hard-coded set of scheduled FOMC dates renders with an explicit banner saying the lookup came back empty. The board degrades to a calendar rather than to an error screen.
  • Per-event errors stay local. A failed result fetch is stored under that event's id with its own retry button, leaving every other row untouched.

Accessibility and motion get the same treatment as correctness: rows are real <button> elements with aria-pressed, focus outlines are defined for every interactive element, and both the pulsing live lamp and the loading blink are disabled under prefers-reduced-motion.

⑧ The published board: prefetch instead of live calls

The component above queries the model from the browser, which needs a runtime that supplies API credentials. A page on a static host has neither, and shipping a key to every visitor is not an option — so the version published here inverts the data flow, the same way Stack handles prices: the searches run ahead of time, server-side, and the page reads their output as static JSON.

GitHub Actions

↓
fetch_market_tape.py
the same four prompts, via the Messages API with web_search
↓
validation
balanced-JSON salvage · field clamping · rows without a parsable date dropped
↓
commit
data/schedule.json · data/results.json
↓

fetches both, then runs the clock: live windows, countdown, day grouping, lamps

What moves to the server is only the part that needs a key and a search: the prompt contracts (§2), the JSON salvage (§3) and the row validation, all reimplemented in scripts/fetch_market_tape.py. Everything time-dependent stays in the browser, because it has to: a committed file cannot know whether a press conference is on air right now. The ET conversion (§4), the state machine (§5) and the 1 Hz countdown run client-side against the viewer's own clock, exactly as described above.

Two behaviours change as a result. The readout no longer refreshes itself every 90 seconds while an event is live — it is as fresh as the last job run, and the page says when that was. And the per-event Find stream & links button is gone: link discovery happens in the same prefetch, so the links are simply there or not.

Running it: add an ANTHROPIC_API_KEY repository secret, allow Actions to write to the repository, then run the Market tape workflow once by hand. Until that first run the board renders empty and says so, with the always-on channels still working. A run costs a handful of search-grounded requests — two schedule queries plus at most six result queries.

⑨ Limits & what it is not

  • It is not a data feed. Schedules, links and figures come from live web search and can be stale, incomplete or simply wrong. The footer of the app says so, and every figure is rendered with its as-of stamp. Nothing here is checked against a primary source automatically.
  • Latency is search latency. A readout appears when a search-grounded model can find a published number — seconds to minutes behind the wire, not milliseconds. This is a board for watching events, not for reacting to them.
  • Coverage is whatever the search returns. Six Fed events and six earnings rows are hard caps, and a company that has not announced simply does not appear.
  • Freshness is the job's cadence. The published board is as current as the last refresh — twice a day on weekdays — not as current as the wire. The original component, which queries the model from the browser, still needs a runtime that supplies API credentials.
  • No trading, no advice. There is no order path, no position state and no recommendation anywhere in it. Research and instrumentation only.
